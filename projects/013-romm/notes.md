# 013 · RomM：理解归纳与研究记录

## 研究范围

本轮目标：把讨论中“有没有游戏、管理和运行分别是什么、有没有加速、对我们有多大价值”整理为一张可作为首页入口的引导图，并提供明确的摘要、依据和扩展条件。

## 理解如何收敛

| 讨论问题 | 最终理解 |
| --- | --- |
| 内部有没有游戏？ | 不附带游戏文件和 BIOS，需要自己提供内容；平台安装不产生游戏库 |
| 是不是只有管理？ | 以游戏库管理为基础，还整合资料、模拟器入口、存档同步、用户和终端；“只有管理”会漏掉使用流程 |
| 能运行吗？ | 通过集成或对接的模拟器运行；浏览器方式使用用户设备，可选串流方式使用服务器 |
| 能加速吗？ | 不把通用性能、帧率提升或网络加速归为其核心能力；模拟器快进单独理解 |
| 没内容是不是没价值？ | 对直接获取内容的目标价值有限；大量已有收藏、多设备或多人使用时，管理和同步的整合收益更明确 |
| 我们开发了一批游戏，可以用它组织吗？ | 可以把自研游戏组织为作品库；发布格式兼容或完成适配后再接入游玩，未公开收录的作品需要自己维护资料 |
| 对我们有什么意义？ | 当前不优先部署试玩，保留作多来源资料融合、用户进度和统一入口的工程参考 |

“直接价值有限”是基于当前需求的判断，不从“没有游戏”推导为项目普遍无价值。RomM 仍可作为已有游戏收藏的管理和使用基础设施。

补充理解：当我们自己生产内容时，RomM 的作品组织价值就成立了。它可以成为自研游戏的目录、资料库和统一入口；自制 ROM 是否能直接玩要核对核心，HTML5、Unity / Godot 导出的 PC 游戏或 EXE 等需评估托管、启动与运行适配。引擎名称不代表兼容格式，收录成功也不代表运行成功。基本管理复用与定制专题门户开发分别记录，避免把它们都归为必须从头开发，或都理解为现成可玩。

## 引导图设计

- 原创 SVG 信息图，导出同内容 PNG，尺寸为 1920 × 3036。
- 入口即说明“游戏由你提供”，随后给出有条件的价值判断。
- 四个板块：内容与平台分工、已有能力及效果、场景价值与意义、扩展效果与投入。
- 区分现有整合、可选部署和格式适配；补充自研作品库的管理价值，定制专题门户仍属于二次开发设想。
- 图中说明资料覆盖不等于可玩范围、存档兼容条件，以及未做运行实测。
- 原始图稿与 PNG 由同一份 `tools/draw_guide.py` 生成；不调用图像模型，不使用上游截图或品牌素材。

## 验证与复现边界

已完成的工作是来源核对、图像渲染与版面审阅、文档与索引校验，不代表运行 RomM 成功。未安装或启动 RomM、数据库、游戏、BIOS、模拟器、掌机客户端或串流服务；未测帧率、延迟、同步冲突或多用户容量。

图像由 Pillow 测量文字、Chromium 渲染。生成工具对文字与画布边界执行检查，并分上部、价值和扩展三段人工查看；结果见 [guide-generation.json](references/guide-generation.json)。仓库内容检查使用 `python scripts/projects.py check`；实际结果见 [verification.json](references/verification.json)。

## 后续重新评估的触发条件

1. 已有一批确实要长期管理的游戏文件。
2. 出现两个以上设备的进度接力需求，能够提供待验证的客户端和存档格式。
3. 需要多人访问、权限与 NAS 集中管理。
4. 有自有或授权内容，并决定开发面向特定用户的游戏门户。

满足条件后，再选择少量游戏验证文件识别、资料正确性、游玩、同步和故障恢复。当前不为没有明确需求的扩展投入部署工作。
