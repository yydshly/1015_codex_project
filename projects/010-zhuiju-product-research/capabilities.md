## 2. 资源如何组织

主要数据在 [resources/resources.json](references/upstream/resources/resources.json)，字段定义在 [schema.json](references/upstream/resources/schema.json)。

| 数据组 | 主要字段 | 可复用价值 | 注意 |
| --- | --- | --- | --- |
| 基础信息 | id、name、url、category、summary、tags | 稳定 ID、分类和检索入口 | URL、简介和域名可能变化 |
| 访问条件 | requires_login、free_level、regions | 记录登录、费用和可达区域 | 是目录记录，需要实际核查 |
| 评分 | more、speed、clean、stable、ease | 将体验拆成多个维度 | 不是持续测得的 SLA |
| 风险 | copyright、safety、privacy、payment | 显式表达未知和风险 | 分类标签不替代合同或审计 |
| 人工核验 | status、last_checked、method、notes | 保留谁在什么时间观察到什么 | 推荐、待审、移除与 HTTP 状态分开 |
| 收录来源 | submitted_by、added_at | 贡献追溯 | 不等于影片版权来源 |
| 展示控制 | featured、featured_order 等 | 数据与 README 排序分离 | 精选不代表所有功能均已验证 |
| 软件信息 | github 等 | GitHub 项目的数据维护 | 与视频媒体的容量无直接关系 |

## 3. 如何收录与维护

### 社区信息进入资源库

[核验记录](references/upstream/reports/verifications.json)中可以看到用户推荐、截图提交、配置地址批量提交和维护者记录。这说明它使用社区发现加维护者整理的方式，但没有足够记录还原每条资源最初的发现者及原始内容供应方。

固定数据中的 105 条 `submitted_by=maintainer` 表示数据库录入归属；其他记录写有贡献者。不能由此得出“105 个资源都是作者自主寻找、拥有或授权”。

### 审核后的自动化

在 [issue-to-resource-pr.yml](references/upstream/.github/workflows/issue-to-resource-pr.yml) 中，维护者评论命令触发处理，并检查评论者拥有 admin、maintain 或 write 权限。工作流解析表单、检查 URL 和重复记录、构造数据、同步展示和检查后提交更改。

文件名含 `pr` 不意味着每次都会开 PR；当前固定版本末尾是提交并推送资源更改。研究结论按实际工作流读取，不由文件名推断。

### 数据与展示分离

[sync-readme.mjs](references/upstream/scripts/sync-readme.mjs)读取资源、核验和可访问记录，按标记区生成分类列表、状态、计数及贡献者等信息。这样可以避免同一条资料在多个表格里手工维护。

固定版本的星数取 `more、speed、clean、stable` 四项平均值，再四舍五入并限制在 1～5；`ease` 没有参与该函数。因此不能仅凭五个评分字段就假设五项等权。

审核工作流对新记录的五项评分默认写入 4.0，并将费用状态设为 unknown、地区设为 GLOBAL。它们是录入默认值，不是测量结果或全球商业授权证据。人工后续可以修改数据，但星数不能被解释为自动测得的播放性能。

### 定时任务

| 任务 | 固定版本行为 | 能证明什么 |
| --- | --- | --- |
| 数据校验 | 脚本检查字段、状态、重复 ID 和跨表引用等 | 数据结构一致性 |
| 可访问检查 | 每日计划运行，也支持手动及相关文件变更触发 | 某时某节点 URL 的 HTTP 响应 |
| 开源项目统计 | 周期更新 GitHub 数据 | 软件仓库信息变化 |
| 周报 | 定时生成并发布 Release | 目录变化整理 |

源码快照仅包含精选研究文件，不是完整上游 checkout；本轮没有在该精简快照里运行全部上游工作流。

## 4. 自动检测到底测了什么

阅读 [check-availability.mjs](references/upstream/scripts/check-availability.mjs)可知：

- 默认超时 15 秒、并发 4、最多尝试 2 次。
- 跟随 HTTP 重定向，发送 Range 请求后取消响应体；没有运行浏览器播放。
- 2xx / 3xx 判为 reachable。
- 401、403、405、429 判为 restricted。
- 其他错误响应或最终网络失败判为 unreachable；部分服务器错误会重试。
- 只处理精选且分类不是 open_source 的资源。
- 每日计划为 UTC 01:00，即北京时间 09:00；计划时间不保证执行准点。

固定报告时间为 2026-10-15 01:26:02 UTC，共 96 条结果，66 可访问、21 受限、9 无法访问。这不是“119 个源有 66 个能看”，也不是影片播放成功率。

检测不会证明页面没有广告、搜索有结果、具体集数可播、字幕正确、地域授权有效或访问者网络顺畅。返回 200 的页面也可能是提示页。因此正式产品应增加搜索、详情、清单、分片、浏览器解码和真实用户质量分层检测。

| 评价维度 | 本轮能给出的判断 | 仍缺什么 |

| 降低寻找入口成本 | 分类目录和维护记录有明确帮助 | 缺少与随机搜索对照的效率实验 |

## 6. 007 的实际实验

有限筛选记录为 17 份配置读取、26 条 HTTP API 调用；部分不同 URL 属于同一上游。只解析公开配置和调用 HTTP，不执行远程 Spider 插件。

样例 ID 168380 的片名、年份和季度信息来自第三方返回，未独立核实影片身份和上线时间。页面显示 8 集，首两集的 HLS 清单及分片抽样返回成功，ffprobe 与浏览器识别出 1920×1080 H.264 / AAC。最终浏览器记录的两集播放时间分别推进至约 31.55 秒和 14.06 秒。

这些数据支持“有真实视频解码和播放”，不支持“完整内容已经核验”。截图展示的是当时第三方画面；媒体权利归相应权利人。详见 [007 报告](../007-zhuiju-source-demo/README.md)与[证据摘要](references/evidence-summary.json)。

## 7. 值得复用与需要补齐的部分

**值得复用：** 单一数据源、稳定 ID、来源和核验分离、人工与自动状态分离、范围明确的健康检查、变更留档、社区审核后自动更新。

**要做站内播放还需新增：** 片目模型、来源适配器、搜索和详情 API、线路与集数解析、播放器、错误恢复、缓存、版权可用范围、限流及质量统计。

**要做商业产品还需新增：** 持续内容供给、明确合同、账户和商业结算、运营管理、供应中断处理、带宽预算以及用户增长和付费实验。

原库最直接的复用价值是资源治理方法。它可以帮助开始研究，但不会替代内容采购和商业运营。
