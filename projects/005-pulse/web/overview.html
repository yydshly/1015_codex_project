01 / CAPABILITY

先分清：额度，还有消耗。

两条通道回答不同的问题。本研究聚焦“哪些模型，在这台机器上用了多少”。

原产品的另一条通道

账号额度监控

复用登录态，通过服务商接口、CLI / 本地服务或状态栏回调，显示额度、余额和重置时间，并提供浮窗、提醒与多账号管理。

回答：这个账号还能用多少？
本次关心的核心价值

本地 Agent 用量统计

读取日志、数据库或已有导出，提取每次调用的模型与计数；校正后按 Agent、模型、项目和日期汇总，再匹配价格。

回答：哪些模型，用了多少 Token？

账号额度百分比不能直接拆成各模型消耗。单看配置中的默认模型，也无法得知每次调用的真实使用量。

02 / UNDER THE HOOD

模型名和 Token 数，来自已有记录。

核心是理解各工具的格式与计数语义，再把它们转换成同一份可加总的增量记录。

  1. 01

    找到来源

    JSONL、SQLite、任务 JSON、OTEL、已有导出

  2. 02

    提取与归因

    模型 ID、时间、输入 / 输出 / 缓存、会话身份

  3. 03

    校正与去重

    累计做差、合并快照、排除分叉重放、处理重叠

  4. 04

    聚合与计价

    按模型 / Agent / 项目 / 日期整理，匹配模型价格

CLAUDE CODE / 会话 JSONL

模型与 usage 在同一条消息中。

message.model + message.usage

同一回复可能写入多个内容块，输出计数持续更新。按 message.id 保留最终计数，再排除跨文件历史副本。

核对读取器 ↗
CODEX / 会话累计快照

当前模型，接住后续用量增量。

payload.model + total_token_usage

通常由 turn context 更新模型，累计 Token 相邻做差。输入含缓存时先拆分；fork 首次基线与历史重放另行协调。

核对读取器 ↗
CURSOR / 预先导出

逐模型统计，需要已有明细。

model + input / output / cache

读取导出的 JSON 或 CSV。该统计通道不自动登录或抓取；重叠导出需要协调，缺事件 ID 的覆盖可能不完整。

核对读取器 ↗

ILLUSTRATION / 合成记录

累计快照，为什么不能直接相加？

逐条读日志，观察重复快照、模型切换和缓存拆分。数据仅用于解释原理。

第 2 / 5 条记录
读到的事件
按记录中的模型归集
模型普通输入缓存读取输出
普通输入 = 输入增量 − 缓存增量；重复累计值产生 0 增量。
客户端模型标签用于归因，不能独立证明服务端实际路由。



API 等价费用
计数与金额，分开核对。
Σ（各类 Token × 对应模型单价） ÷ 1,000,000
ModelPrices 从 models.dev 取价，按原始模型 ID 与别名匹配，再按输入、输出、缓存类型计费，处理适用的阶梯差异。未知价格保留为未定价；估算金额不等于订阅实付。

04 / PRODUCT REFERENCE
对我的价值：实现类似的本地统计能力。
可借鉴的是来源适配、记账语义和完整性表达。这套思路可以独立用于命令行、网页看板或自己的应用。
来源适配器→标准记录→差分与去重→价格目录→聚合查询
可以直接学习
读懂格式，先把数算对。
模型从哪里取、计数是累计还是单次、缓存是否包含在输入中、消息是否被重放。这些细节比做一个图表更决定产品可信度。

可扩展方向
以下是研究建议，尚未在本项目实现。
01
Windows / WSL
分开处理路径、发行版与命令调用；识别镜像记录，保持同一套统计口径。
02
增量与性能
指纹、文件偏移、数据库水位、取消与恢复；结果应能和全量重算对齐。
03
账号与价格快照
只使用可证实的账号身份；保留价格版本，区分 API 等价估算与实际账单。
04
预算与项目分析
按模型、Agent 和项目对比趋势与缓存；按实际需要加入预算预警或脱敏汇总。
