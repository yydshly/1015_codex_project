# GitNexus：能力、原理、研究启发与产品方向

整理日期：2026-10-19，Asia/Shanghai。本研究沿用 2026-10-16 保存的固定 npm `gitnexus@1.6.12` 实验；没有把文档描述、研究推论或产品设想当作新的实跑结果。

## 摘要

GitNexus 把源码中的文件、函数、类型及跨文件关系组织成持久化的代码知识索引，围绕检索、调用链、流程与修改影响提供结构化查询，并通过 CLI／MCP 等接口交给开发者或 AI。网页是其中一种呈现方式。我们的理解是：它更有价值的部分是能回到源码核对的关系与任务上下文；基于同一索引，可以继续探索变更审查、架构导航、Agent 上下文服务和 API 契约检查。现有小样本证明了部分工具能够返回预期关系，也发现了参数 URL 和回调传播缺口；尚不能证明大型项目覆盖率、AI 修复收益或生产可用性。

## 库的能力是什么

| 层次 | 能力 | 典型产出 |
| --- | --- | --- |
| 代码知识索引 | 解析源码实体、绑定跨文件关系并持久化；代码变化后维护索引 | 可查询的文件、符号、调用、导入等关系 |
| 查询与分析 | 检索、符号上下文、有向路径、分组与候选流程、影响与 Git diff 关联 | 与具体调查相关的符号、关系、流程和源码位置 |
| 扩展分析 | 改名预览、API／工具映射、响应字段检查、可选 PDG | 候选修改、接口关联、控制与数据依赖线索 |
| 工具接入与呈现 | CLI／MCP／HTTP、网页；另有需模型的问答与 Wiki | 给工具的结构化结果，给人的关系图、源码与解释 |

它提供调查依据。真实执行路径、性能表现、修改后的业务正确性，需要执行、测试或运行追踪证据。

## 原理是什么

```text
源码
  → 语法解析：识别定义、引用与位置
  → 关系解析：结合导入、别名、作用域和类型规则绑定目标
  → LadybugDB：保存符号与 CALLS、IMPORTS 等关系
  → 检索与结构计算：关键词／可选向量索引、分组、候选流程
  → 任务查询：context、trace、impact、detect_changes 等
  → CLI／MCP／HTTP／网页 → 回到源码、执行与测试
```

AST 是单文件语法结构，跨文件关系的正确性取决于后续绑定规则；数据库让结果可以重复查询。分组是结构上的聚类，候选流程来自静态关系遍历，不能直接等同业务部门边界或线上请求轨迹。图的坐标、颜色、播放和源码联动是本展厅的呈现实现。

## 我们的研究启发

以下是从已有证据形成的判断与设计取舍，不是新增的上游能力或性能结论。

### 1. 应优先核对关系，再设计复杂视图

基础样本找到 11 条预期业务调用，能够区分别名和同名函数；高级样本却没有连上参数 URL 的消费者。这说明某个视图画得完整，不能单独证明索引完整。产品应提供源码位置、关系来源和未覆盖项，让使用者能复核与纠错。

### 2. 结构分析与行为验证应分层组合

impact 和 Git diff 关联能告诉我们该调查哪些符号与流程，但没有预测运费规则的真实结果。5 组金额探针是另外执行样本源码得到的。由此可设计“图谱缩小调查范围 → 运行测试验证行为 → 保存证据”的工作流，分别展示静态候选与执行事实。

### 3. 同一知识索引可以服务不同产品入口

人需要地图、路径和源码；Agent 更需要目标符号、关联关系、版本和有限上下文。界面可以更换，底层知识索引与任务查询仍可复用。产品设计应先定义问题与输出，再决定用图、报告、IDE 面板还是工具接口交付。

### 4. 索引的版本、时效与缺口应成为产品信息

本研究发现 npm 分发 gitHead 与 GitHub 文档 tag 不同，源码等价关系未建立；也保留了参数 URL 与回调案例的漏报。面向真实项目时，应展示代码版本、索引时间、查询范围与已知缺口，并核对更新策略。空结果不能自动解释为没有依赖，confidence 也不能直接当作准确率。

## 可扩展的产品与方向

以下均为本研究提出的产品设想，尚未实现，也没有验证其收益。顺序表示建议先做什么实验，不构成产品成熟度或性能排名。

| 方向与建议阶段 | 给谁解决什么问题 | 可复用的基础 | 必须补齐 | 怎样验证价值 |
| --- | --- | --- | --- | --- |
| 变更审查助手：先做单仓库原型 | 开发者和评审者调查一次修改需要检查哪里 | diff → 符号 → 影响与流程；源码位置 | Git／CI 接入、索引版本核对、测试关联、人工复核 | 标注任务上的遗漏与误报、调查耗时、回归检查是否有用 |
| 仓库接手与架构导航：适合原型 | 新成员快速找到入口、模块与实现链路 | 分组、上下文、调用路径与源码 | 业务标签、模块命名、负责人、索引更新 | 能否给出带源码依据的正确答案，以及定位耗时 |
| Agent 上下文服务：先验证任务收益 | 编程助手按需获取与当前问题相关的代码依据 | query／context／impact，CLI／MCP 接口 | 真实 Agent 接入、权限过滤、上下文预算、失败回退、任务评测 | 在相同代码版本和任务上比较成功率、耗时、Token 与成本 |
| API 契约漂移检查：定向实验 | 前后端协作时发现消费者与提供者的字段偏差 | 路由／工具映射、shape_check 与 api_impact | 框架适配、参数 URL 识别、显式 schema／契约、规则与报告 | 标注路由关联覆盖和字段检查误报；核对真实执行 |
| 跨仓库变更雷达：后续研究 | 多服务团队调查一个契约修改涉及哪些仓库 | 上游文档描述的仓库组与契约连接；本研究未实跑 | 多仓库索引、稳定契约标识、版本对齐、访问控制 | 先用两个小仓库人工核对跨仓库关系，再评估扩大范围 |

可以进一步研究运行追踪或性能采样与静态图谱的关联，用执行证据补充实际路径和耗时。当前没有完成这种整合，不把它列为 GitNexus 已有的实测效果。

## 与同类工具的价值对照

GitNexus 偏向符号关系与开发任务上下文；Ix 偏向持续结构维护与历史追溯；CodeFlow 偏向快速浏览结构、源码卡片和报告。这些能力存在交集，不能把调用链、影响分析或 MCP 接入视为 GitNexus 独有。详见 [完整对比](comparison.md)。Ix 后端未运行，CodeFlow 使用另一套样本，未做三工具同仓库准确率、速度或成本排名。

## 已验证与未验证

- **已验证的小样本能力**：基础 71 实体／131 关系、4 分组／4 候选流程、10 组 context 和 impact、3 次 FTS 查询、路径与 Git diff 关联、循环导入检查。
- **实跑但有覆盖缺口或范围限制**：独立高级图谱 103／154；改名仅 dry-run，4 文件／5 候选含 1 项文本匹配；API 参数 URL 未关联；PDG 7 条控制依赖／3 条变量依赖，回调传播漏报。
- **尚未验证**：向量检索、模型问答与 Wiki、真实 Agent 任务与自动修复、跨仓库组、分支／自动同步／长期维护，以及大型仓库覆盖、索引成本和任务收益。

当前材料足以理解定位、机制与初步选型；工程采用的下一步是用自己的真实项目和固定任务进行验证，不是仅增加展示视图。
